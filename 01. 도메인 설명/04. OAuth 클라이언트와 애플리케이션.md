# 4편. OAuth 클라이언트와 애플리케이션

> **OAuth 클라이언트**는 "우리 서비스에 DataGSM 로그인을 붙이겠습니다"라는 등록증이고, **애플리케이션**은 "우리 서비스는 이런 권한을 따로 제공합니다"라는 등록증이에요.

이 편은 시리즈에서 가장 헷갈리는 부분이에요. 이름이 비슷하지만 하는 일이 완전히 달라서, 하나씩 따로 보고 마지막에 비교할게요.

## 왜 필요한가요?

### OAuth 클라이언트가 필요한 이유

[2편](./02.%20로그인%20%28OAuth%29.md)에서 외부 서비스가 "DataGSM으로 로그인"을 쓸 수 있다고 했어요. 그런데 아무 서비스나 DataGSM 로그인을 쓸 수 있으면 위험해요.

- 가짜 서비스가 DataGSM 로그인 화면을 띄워서 사용자 정보를 빼 갈 수 있어요.
- 로그인 후 사용자 정보를 엉뚱한 주소로 보내게 만들 수 있어요.
- 동의 화면에 어떤 서비스가 정보를 요청하는지 보여 줄 수 없어요.

그래서 DataGSM 로그인을 쓰려는 서비스는 먼저 **OAuth 클라이언트**로 등록해야 해요. 등록할 때 서비스 이름, 로그인 후 돌아갈 주소, 필요한 권한을 미리 정해 두고, DataGSM은 등록된 대로만 로그인을 허락해요.

### 애플리케이션이 필요한 이유

DataGSM이 기본으로 주는 권한은 "학생 정보 조회", "동아리 정보 조회" 같은 DataGSM의 데이터에 대한 권한이에요.

그런데 교내 서비스끼리 서로의 데이터를 쓰고 싶을 때도 있어요. 예를 들어 "급식 알리미"라는 서비스가 있고, 다른 서비스가 급식 알리미의 "급식 평가 등록" 기능을 쓰고 싶다고 해 볼게요. 이때 급식 알리미는 "이 사용자가 우리 서비스의 급식 평가 권한을 허락했는지" 확인할 방법이 필요해요.

**애플리케이션**은 이럴 때 써요. 급식 알리미가 DataGSM에 애플리케이션을 만들고 `meal_write` 같은 **자기만의 권한 범위**를 정의하면, 다른 서비스는 DataGSM 로그인으로 그 권한을 요청할 수 있어요. 사용자는 DataGSM 동의 화면에서 그 권한을 허락하고요.

이렇게 서비스마다 따로 로그인과 권한 시스템을 만들지 않아도, DataGSM 하나로 교내 서비스끼리 권한을 주고받을 수 있어요. 기술 문서에서는 이 기능을 **서드파티 권한 범위**라고 불러요.

## 누가 쓰나요?

| 누가 | 어디서 | 무엇을 |
|---|---|---|
| 외부 개발자 | 개발자 콘솔의 클라이언트 화면 | OAuth 클라이언트 등록, 수정, 삭제 |
| 외부 개발자 | 개발자 콘솔의 애플리케이션 화면 | 애플리케이션과 권한 범위 등록, 수정, 삭제 |
| 관리자 | 개발자 콘솔 | 다른 사람의 클라이언트와 애플리케이션도 수정, 삭제 |

## OAuth 클라이언트 기능

### 클라이언트 등록

개발자 콘솔의 **클라이언트** 화면에서 새 클라이언트를 만들어요. 입력하는 정보는 다음과 같아요.

| 항목 | 설명 |
|---|---|
| 클라이언트 이름 | 개발자가 알아보기 위한 이름 |
| 서비스 명칭 | 로그인 페이지와 동의 화면에 사용자에게 보이는 이름 (예: 급식 알리미) |
| 리다이렉트 URL | 로그인이 끝난 뒤 돌아갈 주소. 여러 개 등록할 수 있어요. |
| 권한 범위 | 이 서비스가 사용자에게 요청할 수 있는 권한 목록. 최소 하나는 골라야 해요. |

리다이렉트 URL을 미리 등록하게 하는 이유는, 등록되지 않은 주소로는 로그인 결과를 보내지 않기 위해서예요. 누군가 로그인 결과를 자기 주소로 빼돌리는 공격을 막아요.

### 클라이언트 ID와 클라이언트 시크릿

클라이언트를 만들면 두 가지 값을 받아요.

- **클라이언트 ID**: 서비스를 구분하는 이름표예요. 공개되어도 괜찮아요.
- **클라이언트 시크릿**: 서비스가 진짜 그 서비스라는 걸 증명하는 비밀번호예요. 절대 공개하면 안 돼요.

클라이언트 시크릿은 **만드는 순간 딱 한 번만** 보여 줘요. DataGSM도 원래 값을 저장하지 않고 알아볼 수 없게 바꿔서 저장하기 때문에, 창을 닫으면 다시 확인할 수 없어요. 화면에도 "반드시 복사하여 안전한 곳에 보관하세요"라고 경고해요.

### 고를 수 있는 권한 범위

클라이언트를 만들 때 고를 수 있는 권한 범위는 **DataGSM에 등록된 모든 애플리케이션의 권한 범위**예요. 여기에는 DataGSM 자신이 제공하는 기본 권한도 들어 있어요.

| DataGSM 기본 권한 | 뜻 |
|---|---|
| 계정 정보 조회 | 로그인한 사용자의 이메일, 권한 등급, 학생인지 선생님인지 |
| 학생 정보 조회 | 로그인한 사용자의 학생(또는 선생님) 정보 |
| 동아리 정보 조회 | 로그인한 사용자의 소속 동아리 |
| 프로젝트 정보 조회 | 로그인한 사용자가 참여한 프로젝트 |

동아리와 프로젝트 정보 조회는 클라이언트에 등록해 두어도 **로그인할 때 따로 요청해야만** 받을 수 있어요. 꼭 필요한 서비스만 받아 가도록 한 번 더 확인하는 셈이에요.

DataGSM도 내부적으로는 "DataGSM"이라는 애플리케이션으로 등록되어 있고, 위 권한들은 그 애플리케이션의 권한 범위예요. 그래서 DataGSM 기본 권한과 다른 서비스가 만든 권한은 같은 방식으로 다뤄져요.

### 클라이언트 수정과 삭제

클라이언트 이름, 서비스 명칭, 리다이렉트 URL은 나중에 바꿀 수 있어요. 권한 범위는 수정할 수 없어서, 바꾸려면 클라이언트를 새로 만들어야 해요. 클라이언트를 삭제하면 그 서비스는 더 이상 DataGSM 로그인을 쓸 수 없어요.

클라이언트는 만든 사람과 관리자만 수정하거나 삭제할 수 있어요.

## 애플리케이션 기능

### 애플리케이션 등록

개발자 콘솔의 **애플리케이션** 화면에서 만들어요. 입력하는 정보는 이름과 권한 범위 목록이에요.

권한 범위마다 **이름**과 **설명**을 적어요.

| 항목 | 예시 | 규칙 |
|---|---|---|
| 권한 이름 | `meal_read` | 영어 소문자, 숫자, `_`, `-`만 쓸 수 있어요. 한 애플리케이션 안에서 겹치면 안 돼요. |
| 권한 설명 | 급식 평가 조회 | 동의 화면에서 사용자에게 보이는 설명이에요. 비워 둘 수 없어요. |

애플리케이션을 만들면 **애플리케이션 ID**가 생겨요. 실제 권한 범위는 `애플리케이션ID:권한이름` 모양으로 쓰여요. 그래서 서로 다른 애플리케이션이 같은 권한 이름(예: `read`)을 써도 헷갈리지 않아요.

### 권한 범위 추가, 수정, 삭제

애플리케이션을 만든 뒤에도 권한 범위를 추가하거나, 이름과 설명을 고치거나, 삭제할 수 있어요.

권한 범위를 삭제하면 그 권한을 고르고 있던 **모든 클라이언트에서도 자동으로 빠져요.** 애플리케이션 자체를 삭제하면 그 애플리케이션의 권한 범위 전부가 클라이언트에서 빠져요.

애플리케이션도 만든 사람과 관리자만 수정하거나 삭제할 수 있어요.

### 애플리케이션 권한이 쓰이는 과정

급식 알리미 예시로 전체 과정을 따라가 볼게요.

1. **급식 알리미 개발자**가 애플리케이션을 만들고 `meal_write`(급식 평가 등록) 권한을 정의해요.
2. **다른 서비스 개발자**가 OAuth 클라이언트를 만들 때 이 `meal_write` 권한을 골라요.
3. **사용자**가 다른 서비스에서 DataGSM으로 로그인하면, 동의 화면에 "급식 평가 등록" 권한이 보이고 사용자가 허락해요.
4. 다른 서비스는 **권한이 담긴 토큰**을 받아요.
5. 다른 서비스가 그 토큰을 들고 급식 알리미에 요청하면, 급식 알리미는 토큰이 진짜 DataGSM이 발급한 것인지, `meal_write` 권한이 들어 있는지 확인하고 요청을 처리해요.

## 한눈에 비교하기

| 구분 | OAuth 클라이언트 | 애플리케이션 |
|---|---|---|
| 한 줄 설명 | DataGSM 로그인을 **쓰는** 서비스 | 권한을 **제공하는** 서비스 |
| 비유 | 놀이공원 **입장객** 등록 | 놀이공원 안의 **놀이기구** 등록 |
| 만드는 것 | 클라이언트 ID, 클라이언트 시크릿 | 애플리케이션 ID, 권한 범위 목록 |
| 정하는 것 | 서비스 이름, 돌아갈 주소, 요청할 권한 | 다른 서비스에 제공할 권한의 이름과 설명 |
| 꼭 필요한 경우 | DataGSM 로그인을 붙이고 싶을 때 | 내 서비스의 기능을 다른 서비스에 권한으로 열어 주고 싶을 때 |

대부분의 서비스는 **OAuth 클라이언트만** 만들면 돼요. 애플리케이션은 내 서비스가 다른 서비스에 권한을 제공해야 할 때만 만들어요.

## 다른 도메인과의 관계

- **계정 (1편)**: 클라이언트와 애플리케이션은 만든 계정에 속해요. 탈퇴하면 함께 삭제돼요.
- **로그인 (2편)**: 로그인 페이지와 동의 화면에 보이는 서비스 이름과 권한 목록은 클라이언트에 등록한 내용이에요.
- **API 키 (3편)**: API 키의 권한 범위(`student:read` 등)와 OAuth 권한 범위는 별개예요. API 키는 데이터를 통째로 가져갈 때, OAuth 권한은 로그인한 사용자의 허락을 받을 때 써요.

## 기억할 용어

| 용어 | 뜻 |
|---|---|
| OAuth 클라이언트 | DataGSM 로그인을 쓰려는 서비스의 등록 정보 |
| 클라이언트 ID | 클라이언트를 구분하는 공개 이름표 |
| 클라이언트 시크릿 | 클라이언트를 증명하는 비밀번호. 만들 때 한 번만 보여요. |
| 리다이렉트 URL | 로그인이 끝난 뒤 돌아갈 주소 |
| 애플리케이션 | 자기만의 권한 범위를 정의하는 서비스의 등록 정보 |
| 서드파티 권한 범위 | 외부 애플리케이션이 직접 정의한 권한. `애플리케이션ID:권한이름` 모양이에요. |

## 한 번 더 정리

- DataGSM 로그인을 쓰려면 OAuth 클라이언트를 등록해야 해요.
- 클라이언트 시크릿은 만들 때 한 번만 보이니 바로 안전하게 보관해야 해요.
- 애플리케이션은 내 서비스만의 권한을 만들어서 다른 서비스에 열어 줄 때 써요.
- DataGSM 기본 권한도 "DataGSM" 애플리케이션의 권한이라서, 모든 권한은 같은 방식으로 다뤄져요.
- 대부분은 클라이언트만 만들면 되고, 애플리케이션은 필요할 때만 만들어요.
