# 도메인 설명 시리즈 작성 가이드

이 문서는 `01. 도메인 설명` 시리즈를 쓸 때 지키는 규칙을 모아 둔 문서입니다.
새 글을 쓰거나 기존 글을 고칠 때 먼저 이 문서를 읽고 시작합니다.

## 시리즈의 목적

- **독자**: DataGSM을 인수인계받는 고등학교 1학년 후배
- **목표**: 후배가 "DataGSM에 어떤 기능이 있고, 각 기능이 무엇을 위해 존재하는지"를 알게 하는 것
- **다루지 않는 것**: Controller, Service, Entity 같은 코드 구조와 세부 로직. 이 부분은 발표자가 따로 설명합니다.

## 글 하나의 공통 목차

모든 편은 아래 순서를 따릅니다. 내용이 없는 섹션은 빼도 됩니다.

1. **한 줄 소개**: 인용문(`>`)으로 이 도메인을 한 문장으로 설명
2. **왜 필요한가요?**: 이 기능이 없으면 생기는 불편함
3. **누가 쓰나요?**: 일반 사용자, 외부 개발자, 관리자 중 누가 어떤 화면에서 쓰는지
4. **기능 살펴보기**: 기능마다 `###` 소제목을 두고 무엇을 하는 기능인지 설명
5. **다른 도메인과의 관계**: 이 도메인이 다른 도메인과 어떻게 연결되는지
6. **기억할 용어**: 이 편에서 처음 나온 용어를 표로 정리
7. **한 번 더 정리**: 핵심을 3~5줄 목록으로 요약

## 문체와 형식 규칙

- 모든 글은 **마크다운**으로 씁니다.
- 문체는 **해요체**를 씁니다. (예: "학생 정보를 관리해요.")
- 코드, 클래스 이름, 패키지 경로는 쓰지 않습니다. 사용자가 보는 화면과 기능 이름으로 설명합니다.
- API 주소는 꼭 필요할 때만 적습니다. 예외로, 권한 범위 이름(`student:read`)처럼 사용자가 화면에서 직접 보는 값은 그대로 적습니다.
- 숫자(만료 기간, 요청량 제한 등)는 실제 설정값과 같아야 합니다. 값이 바뀌면 글도 함께 고칩니다.
- 비유를 적극적으로 씁니다. 다만 비유 뒤에는 실제 동작을 정확히 적습니다.
- 표는 비교나 목록 정리에만 쓰고, 설명은 문장으로 씁니다.
- 제목은 `#` 하나만 쓰고, 섹션은 `##`, 기능은 `###`을 씁니다.

글에서 사이트를 부를 때는 아래 이름을 통일해서 씁니다.

## 용어집

편마다 같은 용어를 같은 뜻으로 씁니다.

| 용어 | 설명 |
|---|---|
| OpenAPI | 학교 데이터를 외부 서비스가 가져갈 수 있도록 공개한 API |
| OAuth | 다른 서비스가 "DataGSM으로 로그인" 기능을 쓸 수 있게 하는 표준 방식 |
| SSO | 한 번 로그인하면 다른 서비스에서 다시 로그인하지 않아도 되는 통합 로그인 |
| API 키 | OpenAPI를 호출할 때 "누가 요청했는지" 증명하는 열쇠 |
| 권한 범위 (scope) | 열쇠나 로그인으로 접근할 수 있는 데이터의 범위 |
| OAuth 클라이언트 | DataGSM 로그인을 붙이려는 외부 서비스의 등록 정보 |
| 애플리케이션 | 자기만의 권한 범위를 정의하는 외부 서비스의 등록 정보 |
| 동의 | 사용자가 외부 서비스에 내 정보 제공을 허락하는 것 |
| 로테이션 | 기존 키를 폐기하고 새 키로 교체하는 것 |
| 웹훅 (Webhook) | 데이터가 바뀌면 DataGSM이 외부 서버에 먼저 알려주는 방식 |
| 요청량 제한 (Rate Limit) | 일정 시간 동안 보낼 수 있는 요청 수의 상한 |

## 사실 확인 기준

글에 적는 기능과 숫자는 아래 저장소의 코드와 기술 문서를 기준으로 확인합니다.

- 서버: `themoment-team/datagsm-server`
- 클라이언트: `themoment-team/datagsm-client` (기술 문서는 `apps/docs`)

## 커밋 규칙

- 마크다운 파일 하나마다 커밋을 하나씩 만듭니다.
- 커밋 메시지는 한 줄로 씁니다. 예: `docs: 계정 도메인 설명 추가`
- 커밋 메시지에 다른 줄(공동 작성자, 세션 정보 등)을 붙이지 않습니다.
